Problem Statement & Motivation
The FinOps Fragmentation & Blind Automation Dilemma
1. Massive Cloud Waste
Epidemic Overspending:
  • Gartner & Flexera report that 30%–35% of multi-cloud enterprise spend is pure waste.
  • Abandoned unattached storage volumes.
  • Zombie compute instances running at <5% CPU.
  • Unassociated public IPv4 reservation fees.
  • Dev/test environments running 24/7 on weekends.
2. Blind Automation Dilemma
Why Engineers Resist Scripts:
  • Naive scripts delete resources based purely on cost without analyzing blast radius.
  • Deleting a detached database backup volume.
  • Stopping an idle VM behind an Application Load Balancer.
  • Corrupting production state without snapshots.
  • Result: Teams disable automation; waste accumulates unchecked.
3. The CloudOptima Solution
7-Layer Governed FinOps:
  • FOCUS 1.0 Normalization: Unifies AWS, Azure, & GCP billing taxonomies.
  • Azure Public Dataset Traces: Real 5-minute CPU telemetry.

Layer 2 & 3: Telemetry & Traces
Utilization Telemetry: Azure Public Dataset VM Traces
Real 5-Minute VM CPU Utilization Traces
Azure Public Dataset Integration:
  • GitHub: https://github.com/Azure/AzurePublicDataset
  • 288 distinct 5-minute readings per 24 hours per VM (2,016 readings over 7-day window).
  • Metrics extracted: avg_cpu, max_cpu, min_cpu, p95_cpu, and memory utilization.
  • Real VM size profiles:
    • Standard_D4s_v5 (4 vCPUs, 16 GB RAM)
    • Standard_B2s (2 vCPUs, 4 GB RAM)
    • Standard_E8s_v5 (8 vCPUs, 64 GB RAM)
Mathematical Idle Instance Formulation
Guarding Against False Positive Outages:
Avg_CPU_7d = (1 / N) * SUM(avg_cpu_i) < 10.0%
AND P95_CPU_7d < 20.0%
  • Why P95 Matters: Periodic batch cron jobs spike to 80% for 10 minutes then idle at 2%.
  • If P95 > 20%, instance is classified as Bursty Batch rather than idle, preventing accidental termination of active workloads.
  • Interactive Chart.js visualizer live on /layer2.

Layer 5: Core Academic Contribution
Multi-Factor Risk Classifier: Explainable Blast Radius
Mathematical Risk Formulation
Risk Score = min(100, Env + Topology + Action + Conf)
Weighted Evaluation Factors:
  • Environment (40% Weight, Max 45 pts): Production (+45), Staging (+20), Dev/Test (+5), Untagged (+25)
  • Topology Blast Radius (30% Weight, Max 35 pts): Behind Load Balancer (+35), Active Disk Mounts (+25), Standalone (0)
  • Remediation Action (20% Weight, Max 20 pts): Volume Deletion (+20), Instance Stop (+15), IP Release (+5)
  • Confidence Metric (10% Weight, Max 10 pts): Boundary Metric (+10), Definitive 0-IOPS (-5)
Governance Policy Routing Queues
Objective Decision Boundaries:
  • [LOW RISK] Score < 35: Auto-Remediation Queue. Zero-touch execution if auto-remediation flag is enabled on cloud account.
  • [MEDIUM RISK] Score 35–69: Human Approval Queue. Enqueued for review by DevOps/FinOps leads with blast radius context.
  • [HIGH RISK] Score ≥ 70: Critical Human Governance. Strictly enforces pre-action snapshot backup before execution.
Layer 6: Execution & Rollback
Safety Engine: Snapshots, Verifier & 1-Click Rollback
Step 1: Dry-Run Simulation Safe Testing
Every action supports dry_run=True mode. Simulates API permissions, cloud payloads, and state transitions without altering live resources.
Step 2: Pre-Action Snapshot Backup Zero Data Loss
Before deleting or stopping any disk, invokes create_snapshot() via cloud API to generate an immutable backup ID (snap-XXXXXX).
Step 3: Governed Cloud Execution API Execution
Applies cloud action (stop instance, delete volume, release IP) via authenticated AWS/Azure/GCP SDKs with full exception handling.
Step 4: Post-Action State Verifier Mathematical Verification
Re-queries cloud APIs post-execution to mathematically verify resource state. Commits realized financial savings in INR (₹) only after verification.
Step 5: Fail-Safe 1-Click Rollback < 2 Sec Recovery
If verification fails or if an operator clicks 'Restore / Rollback', automatically restores the disk snapshot or restarts the VM instantly.
